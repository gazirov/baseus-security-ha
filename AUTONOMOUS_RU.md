# Автономный клиент: экспериментальный direct UDP backend

**Русский** | [English](AUTONOMOUS_EN.md)

Упаковка для Home Assistant Container с расписанием, историей и NAS-архивом:
[home_assistant/README_RU.md](home_assistant/README_RU.md).

`baseus_autonomous.py` не использует планшет/ADB и не читает Android config.
Он входит в облако по логину/паролю, получает **свежий** список устройств и
последовательно пытается получить JPEG с каждого. Cloud `online_status` не
считается доказательством доступности: спящие камеры тоже проверяются.
Устройства с `camera_on=0` пропускаются, их выключенное состояние не меняется.

**Экспериментальный клиент:** пользователь подтвердил свежий JPEG из полного
live-сеанса, в том числе без `--bind-address` и без `--interface-index`.
Эти параметры остаются необязательными для диагностики, VPN не считается
доказанной единственной причиной прежних сбоев. Подтверждены P2P, XM login и
расшифровка видео. Декодер также получил JPEG 2304x1296 из реального PCAP.
Поддерживается XM/PPCS direct UDP путь, но не relay/TCP,
Tuya, CAT/DDMPP и другие модели протокола. Если direct не устанавливается,
будет ошибка, а не картинка из кэша. Успешный XM login подтверждён live;
неизвестный ответ отклоняется.

## Запуск на Windows PowerShell

```powershell
& .\.venv\Scripts\python.exe -m pip install -r requirements-autonomous.txt
& .\.venv\Scripts\python.exe .\baseus_autonomous.py login
& .\.venv\Scripts\python.exe .\baseus_autonomous.py cameras
& .\.venv\Scripts\python.exe .\baseus_autonomous.py capture-all --wake
```

При `login` email вводится обычным приглашением, пароль — скрытым. Не отправляйте
пароль в чат и не указывайте его в аргументах процесса. Для unattended работы
доступны `BASEUS_ACCOUNT`/`BASEUS_PASSWORD` из защищённого окружения для явной
команды `login`. **Автоматический login отключён**, включая отсутствие token
и 401/403: `cameras`/`capture-all` используют только сохранённую сессию.
Пользователь наблюдал выход остальных устройств после Python-login; причина
не установлена. Явный `login` предупреждает о риске, но не устраняет его.

Linux: те же команды с Python активированного venv вместо Windows-пути.

Опции: `--country RU`, `--state state`, `--output captures/autonomous`,
`--timeout 120`, `--connect-timeout 45`. `--wake` включает штатный MQTT WatchDevice перед каждой
попыткой; без него wake не отправляется. UDP handshake занимает до 45 секунд,
затем действует отдельный XM/JPEG deadline. Оба таймаута настраиваются до 300
секунд. DNS имеет системный timeout. Discovery запрашивается не чаще раза в
секунду до connect deadline; punching повторяется отдельным таймером раз в
0,5 секунды. Увеличение timeout больше не замедляет punching. Hello отправляется
однократно каждому discovery endpoint, а не на каждом раунде.

## Диагностический лог

```powershell
& .\.venv\Scripts\python.exe .\baseus_autonomous.py capture-all --wake --connect-timeout 60 --timeout 180 --verbose
```

Лог пишется в stderr и `logs/autonomous.log` (ротация 2 MB, две резервные
копии). `--log-file` меняет путь. JSON-результат остаётся в stdout.
INFO показывает wake, DNS, раунды discovery, число candidates, установленный
peer, XM login, команды видео, первый media frame, JPEG и безопасную причину
ошибки. `--verbose` добавляет только типы/размеры пакетов, номера каналов и
sequence. Адреса peer, DID, payload, токены и ключи не выводятся; DEBUG внешних
HTTP/MQTT библиотек не включается.

В `last-run.json` добавлены `failure_stage` (`prepare`, `connect`, `xm_login`,
`video`, `decode`) и `error_code`. Это дополняет существующий `error_stage`.
Произвольный текст исключения не сохраняется. Ожидание данных прерывается для
отправки XM keepalive каждые три секунды, не продлевая общий frame deadline.
Дополнительно лог содержит числовые статусы `P2PReqAck` и количество публичных
NAT mappings (с ограничением памяти); сами адреса не сохраняются. ACK discovery
не считается подтверждением готовности peer или авторизации камеры.

Если облако возвращает HTTP 500 с JSON-кодом `100401`/`401`, это теперь
классифицируется как отказ авторизации, а не обычная ошибка сервера. Клиент
останавливается без login и без повторных wake. Истечение и отзыв token этим
ответом не различаются. Ранее сохранённая сессия давала HTTP 500 / `100401`;
в последних проверках облачные запросы прошли без нового login.

## Повторные попытки при нестабильной связи

По умолчанию `capture-all` делает **до трёх попыток на камеру** с паузой
**20 секунд** между ними. Пример с явно заданными параметрами:

```powershell
& .\.venv\Scripts\python.exe .\baseus_autonomous.py capture-all --wake --attempts 3 --retry-delay 20 --verbose
```

`--attempts` допускает 1, 2 или 3; `--retry-delay` — от 0 до 300 секунд.
С включённым `--wake` перед каждой попыткой выполняется новый MQTT WatchDevice
с новой корреляцией ответа. Без `--wake` MQTT не используется ни на одной
попытке. Старый P2P-сеанс закрывается до паузы, новая попытка открывает новый
socket и получает candidates заново. После успеха повторов нет.

Повторы разрешены только для известных временных сбоев: timeout, отсутствие
ACK, транспортные ошибки, потеря peer и неподтверждённое MQTT-пробуждение.
Отказ login/wake, неизвестные форматы и ошибки расшифровки/сохранения не
повторяются. AuthError останавливает запуск без автоматического login.
После исчерпания попыток скрипт переходит к следующей камере.

Лог показывает номер попытки, запланированную паузу и признак `retry`.
JSON содержит `attempts` — фактически выполненное количество попыток
(для выключенных камер 0). После успешного повтора старые поля ошибок убираются.
Таймауты применяются к каждой попытке отдельно, поэтому максимальное время
запуска растёт; при стандартных параметрах три полных попытки могут занять
более восьми минут с учётом wake и пауз. Это не заменяет relay fallback.

## Результаты

JPEG сохраняются атомарно в `captures/autonomous`; имена генерируются из хэша
SN, UTC-времени и случайного суффикса. Cloud names/SN не используются как пути.
`last-run.json` содержит результат каждого устройства: `ok`, `error` или
`disabled`. Ошибка одной камеры не останавливает следующие. Новые снимки
получаются только из текущего P2P-сеанса; старый кадр не подставляется.

Exit codes: `0` — нет ошибок, `2` — ошибки отдельных камер, `1` — ошибка входа,
списка или запуска, `130` — отмена. Пустой список возвращает пустой результат.
В `error` сохраняется тип исключения и безопасная стадия
`wake`/`capture`/`save`, а не текст сторонней ошибки с возможными секретами.

Сессионный token сохраняется в существующий `state/session.json`; защитите эту
папку от чужого чтения. P2P-пароль, service string, transport key, wake key и
MQTT credentials используются в памяти, не записываются в результат/лог.

## Что проверено

- Schema списка, дубликаты, неполный список, изоляция ошибок и безопасные пути.
- Direct handshake с fake UDP peer: DID/source проверки и deadline.
- Настоящий localhost UDP обмен, DRW ACK/reordering, закрытие session.
- XM assembly, AES, отрицательный login и очистка после ошибки.
- Синтетический login→video→JPEG сценарий; реальный H.264→JPEG через PyAV.
- Transport protection: совпадение со штатными encrypt/decrypt ARM64-функциями
  на шести синтетических векторах.
- 143 полных media frames из IN разобраны по заголовкам без расшифровки
  реального payload. Это проверка framing, не проверка JPEG с камеры.

Тесты: `python -m unittest discover -s tests -q`.
PCAP/native codecs: `python -m analysis.verify_ppcs_codecs`.

Свежий JPEG после исправления HEVC подтверждён пользователем. Следующая
проверка — повторяемость результата. Новый login
для этой проверки не нужен при действующей сессии. Relay negotiation требуется
для NAT, через который direct не проходит. Home Assistant подключать после live gate.

## Явный LAN-маршрут для P2P на Windows

При отладке Windows выбирал UDP-маршрут через VPN-интерфейс с адресом
`10.66.133.38`, а планшет подключался по обычному LAN. После разрешённого выбора
LAN-интерфейса утилита получила punch/ready и ответ камеры на login за несколько
секунд. VPN и системные маршруты не отключались и не изменялись.

Для текущего ПК локальный адрес — `192.168.88.36`, индекс LAN-интерфейса — `5`:

```powershell
& .\.venv\Scripts\python.exe .\baseus_autonomous.py capture-all --wake --attempts 3 --retry-delay 20 --bind-address 192.168.88.36 --interface-index 5
```

Обе опции относятся только к PPCS UDP sockets, включая сокет определения
локального адреса. Windows `IP_UNICAST_IF` применяется per-socket; индекс
передаётся в network byte order. HTTPS, MQTT и DNS используют прежние настройки.
По умолчанию явного выбора интерфейса нет. При ошибке его выбора нет скрытого
возврата к VPN-маршруту. `--interface-index` поддерживается только на Windows;
`--bind-address` принимает конкретный локальный IPv4. Один bind без выбора
интерфейса не является универсальной гарантией обхода VPN.

Адрес и индекс могут измениться после переключения сети. Проверка:

```powershell
Get-NetIPAddress -AddressFamily IPv4 | Select-Object InterfaceAlias,InterfaceIndex,IPAddress
```

Входящие control frames камеры используют version 0; это теперь поддержано
наряду с version 1. Реальный SDK проверяет строковый `result: "ok"`; отказ и
противоречащие коды ошибок не принимаются как успешный login. HEVC/H.264
определяются по Annex-B parameter sets: у проверенной S1 видеопоток HEVC, хотя
старый XM codec bit давал hint H.264. Подтверждённый офлайн-JPEG находится в
`diagnostics/pcap_decoded_hevc_frame.jpg` и никогда не подставляется в результат
новой съёмки.

## Заряд батареи

`cameras` и `capture-all` теперь включают поля:

```json
{"battery_percent": 96, "battery_source": "cloud_device_info"}
```

Источник — `device_info.battery` из свежего запроса списка устройств, то есть
последний переданный камерой в облако заряд. Это **не отдельный live-замер**:
возраст самого показания облако в этом поле не сообщает. Нет дополнительных
пробуждений или подключений. Заряд доступен и при ошибке снимка/выключенной
камере. При отсутствующем или некорректном значении оба поля равны `null`;
принимаются только целые проценты 0..100, без преобразования неизвестных схем.

SDK содержит отдельную P2P-команду `101` (`getCameraBattery`), но её реальная
схема ответа пока не проверена, поэтому live-измерение этой командой не заявляется.

## Дата и время на снимке

В двустороннем PCAP первый декодированный кадр не содержит даты, но на 10-м
дата уже есть в самом изображении; она присутствует и на 30-м/60-м кадрах.
Сравнение сохранено локально в `diagnostics/pcap_osd_comparison.jpg`.
По умолчанию клиент возвращает первый доступный JPEG, что может опережать
включение штатного OSD камеры.

Чтобы дать OSD время появиться, пропустите первые 10 декодированных кадров:

```powershell
& .\.venv\Scripts\python.exe .\baseus_autonomous.py capture-all --wake --skip-frames 10
```

`--skip-frames` допускает 0..300, по умолчанию 0. Затем возвращается следующий
декодированный JPEG. Пакеты и неполные кадры не считаются. Общий frame timeout
не продлевается; при нехватке кадров возвращается ошибка, а не ранний снимок.
Настройки камеры не изменяются, время ПК поверх картинки не рисуется.
Появление OSD не определяется автоматически: 10 кадров — отправная точка по
проверенному PCAP, не гарантия для каждой попытки. Новая опция проверена
синтетическими тестами, результат нового live-сеанса с ней ещё не проверен.
